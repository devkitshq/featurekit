# The conformance corpus

`tests/conformance/` · `tools/gen-conformance.mjs` · §9.5

A language-agnostic JSON corpus that every SDK in every language runs. It is
the specification; this TypeScript implementation is just the first thing to be
held to it.

```
tests/conformance/
  bucketing.json    28 cases: {prefix, salt, value} -> expected integer
  evaluation.json   20 cases: {snapshot, context, flagKey} -> expected detail
  cuckoo.json       1,003 members + 1,000 known non-members + the pinned header
  conformance.test.ts   the runner
```

Regenerate with `node tools/gen-conformance.mjs`.

## Rule 1: the corpus must not certify the implementation against itself

> Expected values are computed by hand from the specification, not captured
> from the JS implementation. A corpus generated by the reference
> implementation certifies that implementation against itself. — §9.5

This is not a stylistic preference. It is the lesson of §9.4: r1's bucketing
rounded 96.5% of hashes past `MAX_SAFE_INTEGER`, and a corpus captured from it
would have recorded those rounded values as "expected" — so a Go SDK doing the
arithmetic **correctly** would have failed the corpus that exists to prevent
divergence.

You cannot literally hand-compute murmur3. So `tools/gen-conformance.mjs` is an
**independent transcription of the specification that shares no code with
`src/sdk/`**:

| | production (`murmur3.ts`) | generator (`gen-conformance.mjs`) |
| :-- | :-- | :-- |
| Arithmetic | `Math.imul`, int32 | `BigInt`, masked to 2^32 |
| UTF-8 | `TextEncoder` + ASCII fast path | manual RFC 3629 encoding |
| Tail | explicit `if` chain | explicit `if` chain, written separately |
| Division | `Math.floor(raw * 1e5 / 2^32)` | `(raw * 100000n) >> 32n` |

Two implementations, written from the same published algorithm, agreeing on 28
cases including non-ASCII keys and boundary buckets. That agreement is
evidence. A single implementation agreeing with itself would not be.

The **evaluation** corpus needs no such trick: its expectations are which
variation and which reason, reasoned directly from the §9.1 precedence table.

## Rule 2: the hard cases by construction, not by luck

> The corpus includes non-ASCII context keys and boundary-adjacent buckets by
> construction — the two cases where implementations diverge and random
> fixtures never land. — §9.5

**Non-ASCII.** `usr_josé`, `日本語`, `مرحبا`, `🚀`, `café_🚀_日`, plus NFC `"é"`
and NFD `"é"` as separate cases — those are different byte sequences and
**must** bucket differently. An SDK that normalises Unicode fails here, which
is the point.

**Boundary buckets.** The generator *searches* for context keys that hash to
exactly 0, 1, 9999, 10000, 10001, 49999, 50000, 99998 and 99999. These are
where an off-by-one in `b < cursor`, or a float cursor, changes the answer.

The boundary keys are found **under the flag key the corpus actually evaluates**
— the flag key is part of the hash prefix (§9.3), so a key that sits on a
boundary for one flag is an ordinary key for another. Getting this wrong was a
real bug in the first draft of the generator, caught by the corpus runner.

**Both negation polarities.** The M1 exit criteria call for negated clauses
against unresolved segments *in both directions*, because that is the §22.3
leak. The corpus carries a positive and a negated segment clause against an
unresolvable segment, and both must fail the rule closed. A meta-test walks the
parsed corpus to assert both polarities are actually present, so the coverage
cannot quietly disappear.

## The cuckoo fixture

A byte-exact cuckoo table cannot be hand-computed, and claiming otherwise would
be worse than saying so. What the fixture does instead:

- **The header is hand-specified** from the wire format — magic, format
  version, fingerprint width, slots per bucket, and the derived bucket count
  (1,003 members / (4 x 0.8) = 313.4, so 314, so `nextPow2` = 512 buckets, so
  `bucketsLog2 = 9` and a total of `16 + 512 * 16` bytes). The runner asserts
  every one.
- **1,003 known members and 1,000 known non-members** are listed, including
  non-ASCII members — which is where a byte-vs-code-unit port breaks. Every
  member must be found and no non-member admitted: at 32-bit fingerprints a
  positive is membership, so there is no false-positive budget to hide in.

A porting SDK must read *these bytes* and find *these members*, which is the
property that actually matters.

## Running it

```bash
npx vitest run tests/conformance      # 57 assertions
```

A future Go or Python SDK reads the same three JSON files and asserts the same
outcomes. That is the whole design: the corpus travels, the implementation does
not.

## Wire formats

The corpus ships encoded bytes as well as outcomes, so a porting SDK is checked
against what the encoder actually writes rather than against a description of
it. `cuckoo.json` carries a whole filter as `filterBase64`; decode it and look
every member up.

### Cuckoo filter wire format (`FKCF`)

| Offset | Size | Field |
| --: | --: | :-- |
| 0 | 4 | magic, ASCII `FKCF` |
| 4 | 1 | format version — currently `2` |
| 5 | 1 | fingerprint bits — always `32` |
| 6 | 1 | log2 of the bucket count |
| 7 | 1 | slots per bucket — always `4` |
| 8 | 4 | seed, little-endian `uint32` |
| 12 | 4 | member count, little-endian `uint32` |
| 16 | … | the table |

The table is `bucketCount` buckets of four slots, each slot a little-endian
`uint32`: 16 bytes a bucket.

**A slot of zero is empty**, which is why a fingerprint that hashes to zero is
remapped to `1`.

Lookup uses partial-key hashing, and every constant here is part of the format:

```
h                = MurmurHash3_x86_128(utf8(key), seed)   // four uint32 words
i1(key)          = h[0] & mask
fingerprint(key) = h[1]                                    (0 -> 1)
i2(i1, fp)       = (i1 XOR (fmix32(fp ^ seed ^ 0x5bd1e995) & mask)) & mask
```

where `fmix32` is MurmurHash3's finaliser, `h[0]` and `h[1]` are the first two
little-endian words of the 128-bit output, and `h(fp)` is forced non-zero — at
zero the alternate bucket would equal the primary and every item would have half
the homes the table was sized for. Masking after the XOR is
what makes `i2` an involution, and it is exact only because `bucketCount` is a
power of two.

### What the port does not cover

It reads filters; it does not build them. Encoding is not something a consuming
SDK does, and a byte-exact table cannot be derived by hand — which is why
`cuckoo.json` carries encoder output and says so.
